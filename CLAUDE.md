# GramBas — заметки для Claude

Форк официального Telegram для Android (DrKLO/Telegram), собирается под именем
**GramBas**, пакет `com.rework.grambas`, репозиторий `0siriss/telegram_gx`.

## Границы проекта

Работа по этому аккаунту касается только форка GramBas. Есть старый побочный
проект (Telegram-X с патчем обхода DPI, собирался отдельными APK) — он
неактивен, к этому репозиторию не относится, продолжать его не нужно.

## Главное про архитектуру форка

`patches/fork-changes.patch` — единый источник истины для всех доработок форка
(49 файлов). Рабочее дерево `master` — это свежий upstream с уже наложенным
этим патчем. Файлы `.github/workflows`, `patches/` и `CLAUDE.md` в патч
НЕ входят: авто-апдейт восстанавливает их отдельно из предыдущего коммита, и
дублирование в патче давало конфликт при повторном наложении.

Отсюда главное правило: **правка исходников без перегенерации патча будет
потеряна** при следующем авто-апдейте, потому что он делает `git reset --hard`
на upstream и восстанавливает поверх только `.github/workflows`, `patches/` и
этот файл. Меняешь код форка — обновляй патч.

## Что уже работает (проверено на телефоне)

Это известный рабочий набор, спекулятивно рефакторить его не нужно.

Обход блокировок, нативный слой в `TMessagesProj/jni/tgnet/TLSHello.cpp`,
`ConnectionSocket.cpp` и `TgNetWrapper.cpp`. Начиная с upstream 13.0.2 сам
класс ClientHello вынесен апстримом в `TLSHello.h`/`TLSHello.cpp`, профили
форка и настраиваемый ECH живут там же:

- исправление расширения ECH, ID настраивается, по умолчанию `0xfe0d`;
- профили браузерного фингерпринта: Chrome, Firefox, Safari, Edge, Random, с ротацией;
- фрагментация TLS ClientHello;
- DPI shaping: размер записей, startup cover, джиттер таймингов. Массовые
  соединения (загрузки) от джиттера освобождены, иначе он режет скорость.

Настройки прокидываются из Java через `ConnectionsManager.setTls*` и
`setDpiShapingConfig`, UI живёт в `ProxySettingsActivity`.

Свой экран настроек `GramBasSettingsActivity`, флаги — статические методы в
`MessagesController`:

- anti-recall, показ удалённых отправителем сообщений. Тонстоуны хранятся в
  таблице `recalled_messages(uid, mid, recalled_date)`, миграция в
  `DatabaseMigrationHelper` — ступень 179 -> 180, `LAST_DB_VERSION` 180. Та же
  ступень догоняет апстримную таблицу `welcome_messages` для установок,
  пришедших с форкового 12.10.1: там user_version 177 занимал anti-recall, а
  апстрим позже отдал 177 своей таблице, поэтому она не создавалась;
- показ числового ID в профиле пользователей, групп и каналов, нажатие
  копирует его. Строка `userIdRow` в `ProfileActivity`, у чатов появляется
  внутри существующей инфо-секции;
- сохранение самоуничтожающихся медиа;
- разрешение скриншотов и подавление уведомления о скриншоте в секретных чатах;
- фоновая предзагрузка входящих голосовых;
- скрытие спонсорских сообщений и рекламы в видео, а также всех промо-диалогов:
  запрос промо-инфо не отправляется, сохранённый диалог сбрасывается, выключение
  переключателя запрашивает его заново;
- keep-alive: `ConnectionKeepAliveService` держит foreground-сервис, чтобы не
  засыпало MTProto-соединение. Нужен потому, что настоящий FCM push не работает
  с самоподписанным APK и собственным проектом Firebase. Есть дебаунс, он
  предотвращает падение при старте foreground-сервиса.

Встроенный апдейтер: `GithubUpdaterController` плюс `UpdateAppAlertDialog` и
`UpdateLayout`. Опрашивает последний релиз `0siriss/telegram_gx` и предлагает
поставить `app.apk`.

Имя приложения на телефоне — **Telegram**, как в апстриме: строки `AppName` и
`AppNameBeta` в `res/values/strings.xml` форк не переопределяет. Раньше патч
менял их на GramBas (ребрендинг v2.1), с v2.4 это откатано по просьбе
пользователя. Имя GramBas осталось только там, где речь о самом форке: пункт
и экран настроек, строка версии, заголовок релиза.

Версия форка показывается в настройках рядом с версией Telegram, берётся из
`BuildConfig.FORK_VERSION_TAG`. В CI значение определяет первый шаг `build.yml`
(из тега при push, из входного параметра при ручном запуске), локально
откатывается на `git describe --tags`.

Пункт GramBas в `SettingsActivity` имеет id 100: id берём из диапазона 100+,
иначе апстрим занимает номер своим пунктом и сборка падает на
`duplicate case label`. На 13.0.2 так и вышло с id 24.

## Раздел MAX (модуль TMessagesProj_Max)

Поддержка мессенджера MAX отдельным аккаунтом. Живёт в своём Gradle-модуле и в патч
НЕ входит: авто-апдейт восстанавливает каталог `TMessagesProj_Max` и `.gitmodules`
отдельно, рядом с `.github/workflows` и `patches/`.

Границы, которые нельзя размывать:

- сеть MAX — свой TLS-сокет внутри ядра на Rust, `ConnectionsManager` и нативный tgnet
  не участвуют; настройки маскировки форка относятся только к FakeTLS поверх MTProto;
- состояние аккаунта MAX — `MaxStore` (свои SharedPreferences), слоты `UserConfig`
  остаются за MTProto;
- данные MAX — свои модели, в `MessagesStorage` ничего не пишется;
- зависимости строго в одну сторону: модуль MAX видит `TMessagesProj` (тема,
  компоненты, `BaseFragment`), а `TMessagesProj` знает о нём только через
  `MaxSection` — интерфейс с провайдером, который подставляет `ApplicationLoaderImpl`.

Ядро протокола — подмодуль `TMessagesProj_Max/kolibri` (KometTeam/kolibri, Rust,
лицензия MIT или Apache 2.0). Kotlin-обёртка берётся прямо из подмодуля через
`sourceSets`, копий в репозитории нет. Нативная библиотека `libkolibri_kotlin.so`
собирается в CI шагом «Build MAX native core» только под arm64-v8a и armeabi-v7a;
на остальных архитектурах `MaxNative.available` вернёт false и пункт раздела в
настройках GramBas не показывается.

Авторизация MAX требует отпечаток клиента: ядро считает его из дайджестов
официального приложения MAX, то есть сервер видит нас как официальный клиент. Это
обязательный шаг протокола, но означает риск блокировки аккаунта — в
пользовательских текстах про раздел об этом сказано прямо.

Push-уведомления для MAX невозможны: сервер отправляет их через Firebase-проект MAX,
где зарегистрирован только пакет официального приложения. Уведомления работают
только пока живо соединение, то есть через наш переключатель удержания.

Интерфейс раздела (v2.4.11): главный экран `MaxDialogsFragment` — вкладки «Чаты» и
«Контакты», поиск, «Найти по номеру», «печатает…» и галочки прочтения в превью.
Переписка `MaxChatFragment` в духе Telegram: шапка с аватаркой и статусом («в сети»,
«был(а)…», «печатает…»), нажатие на шапку — профиль `MaxProfileFragment` (у группы —
участники); обои темы; пузыри с временем, «изм.» и галочками ✓/✓✓; пересылки и цитаты
ответов; фото и превью видео (`MaxImages.bindImage`), файлы и голосовые строкой с
кнопкой; разделители дат; догрузка истории вверх; меню по долгому нажатию — ответить,
копировать, переслать, изменить, удалить (у себя или у всех), повторить отправку;
скрепка — отправка фото из галереи (ужимаем до 2560px JPEG 87) и файлов до 100 МБ.
Открытие: фото на весь экран с «Сохранить» (`MaxMedia`), видео — внешним плеером по
ссылке опкода 83, файлы — через DownloadManager в «Загрузки/MAX» по ссылке опкода 88,
голосовые — `MaxAudio` (MediaPlayer по прямой ссылке `url`), геопозиция — картами.
Уведомления о входящих — `MaxNotifier`, свой канал «Сообщения MAX», работают пока жив
процесс (переключатель удержания). Подписи статусов — `MaxText`.

Оформление сообщений (v2.4.12) — из деталей самого Telegram, `MaxBubbles`: пузырь —
наследник `MessageDrawable` (хвостик, скругления по настройке, градиенты темы; красит
себя только после `setTop`, поэтому зовём его в каждом `draw`), подряд идущие сообщения
автора склеиваются (`topNear`/`bottomNear`: имя у первого, хвостик у последнего), место
под хвостик — 17dp со стороны хвоста и 11dp с другой; галочки — `msg_check_s` +
`msg_halfcheck_s` в цветах `key_chat_outSentCheck(Read)`, часики — `MsgClockDrawable`,
в списке чатов — `list_check`/`list_halfcheck`; эмодзи — `Emoji.replaceEmoji`;
сообщение из 1–3 эмодзи — крупно и без пузыря; время — в конце последней строки
(невидимый промежуток шириной с подпись времени), у фото без подписи — поверх картинки
на тёмной плашке; размер шрифта — `SharedConfig.fontSize`.

Голосовые (v2.4.12) — `MaxRecorder`: кодировщик Opus самого Telegram
(`MediaController.startRecord/writeFrame/stopRecord`, закрытые — через рефлексию;
пакет `org.telegram.messenger` целиком в keep у R8). AudioRecord 48 кГц моно, кадр
1920 байт = 20 мс; прямой буфер AudioRecord заполняет всегда с начала, поэтому кадр
читается целиком. Загрузка — опкод 82 `{uploaderType: 1, type: 2, count: 1}` →
`info[0] {url, token}`, `uploadFile`, вложение `{_type: AUDIO, token, duration (мс),
wave}`; волна — 80 значений 0..120, как у Komet. Нативный Opus Android сервер, по опыту
Komet, не дообрабатывает. Кнопка: пустое поле — микрофон, во время записи —
«отправить» и «Отмена».

Кеш (v2.4.12) — `MaxCache`, файлы в `filesDir/max_cache`: чаты и люди из ответа на
вход, адресная книга, первая страница истории каждого чата — ответы сервера как есть.
Список и переписка показываются из кеша сразу, потом обновляются; выход стирает кеш.

Сессию нельзя освобождать (`Session.close`) сразу после отключения: цикл пушей и
запросы в этот момент ещё внутри нативного объекта, и `sessionFree` вызывает
обращение к удалённой памяти в Rust — падает весь процесс (так «Обновить» ронял
приложение в v2.4.11). Старая сессия только отключается и освобождается через 30 с
(`retire`), ссылка на неё держится до этого, чтобы её не освободил сборщик мусора.

Вёрстка, на которой уже обжигались:

- шапку чата кладём в `ActionBar` с явной высотой `getCurrentActionBarHeight()` и
  `topMargin` = высота строки состояния. `ActionBar` раскладывает чужих детей от
  `lp.topMargin` без своего отступа, и с нулевым отступом имя рисовалось под часами;
- обои — наследник `SizeNotifierFrameLayout` с `isActionBarVisible() = false` и
  `setOccupyStatusBar(false)`: по умолчанию он сдвигает фон на высоту шапки (в Telegram
  этот слой лежит под шапкой), и под ней оставалась пустая полоса.

Протокол, сверено с Komet:

- адресная книга — опкод 8 `{contactsSync: 0}`, ответ `contacts`;
- люди по id — опкод 32 `{contactIds: [...]}`. Диалоги имён не несут: имя и аватарка
  собеседника берутся из контактов, поэтому недостающих дозапрашиваем (`resolveMissing`);
- имя человека — запись `names` с типом CUSTOM, иначе ONEME, иначе любая;
- id личного диалога = мой id XOR id собеседника, «Избранное» — чат 0;
- участники чата — словарь «id -> отметка прочтения»; отметка ≥ времени сообщения —
  прочитано (✓✓). Новые отметки — пуш 130 `{chatId, userId, mark}`;
- прочтение — опкод 50 `{type: READ_MESSAGE, chatId, messageId, mark: время}`;
- присутствие — `presence` в ответе на вход и опкод 35 `{contactIds}`; `status` 1 —
  в сети, `seen` — секунды эпохи; пуш 132 `{userId, presence}`;
- набор текста — опкод 65 `{chatId, type: TEXT}`, пуш 129 `{chatId, userId}`;
- история — опкод 49, `from` = время самого старого показанного, `backward` = сколько;
- ответ — `link {type: REPLY, chatId, messageId}`, в пришедшем — `link.message`;
- пересылка — опкод 64 с `link {type: FORWARD, chatId, messageId}`, у пришедшего
  содержимое лежит в `link.message`, имя канала — `link.chatName`;
- правка — опкод 67 `{messageId, chatId, text, elements}`, приходит пушем 128 со
  `status: EDITED`; удаление — опкод 66 `{messageIds, chatId, forMe, itemType}`, пуш 142;
- фото — опкод 80 `{count: 1}` → `url`, загрузка `uploadPhoto` ядра, токен из ответа
  CDN `photos.*.token`, вложение `{_type: PHOTO, photoToken}`; файл — опкод 87 →
  `info[0] {url, fileId, token}`, `uploadFile`, вложение `{_type: FILE, token}`. Пока
  сервер обрабатывает вложение, опкод 64 отвечает «…not.ready» — повторяем раз в секунду;
- ссылка на файл — опкод 88 `{fileId, chatId, messageId, itemType}` → `url`; на видео —
  опкод 83 `{messageId, chatId, token, videoId}`; у голосового прямая ссылка в `url`;
- незнакомый чат из пуша — опкод 48 `{chatIds: [...]}`; участники группы — опкод 59
  `{type: MEMBER, marker, chatId, count}`.

Встраивание в Telegram (v2.4.13, правки в патче форка). Пользователь просил, чтобы MAX
был встроен «практически бесшовно»:

- вкладка MAX в нижней панели `MainTabsActivity` между «Звонками/Настройками» и
  профилем. С ней `POSITION_PROFILE` = 4 вместо 3 (поля стали нестатическими,
  `indexToPosition` — тоже), массив вкладок на 6, ширина панели 410dp. Наличие вкладки
  решается один раз при создании экрана: `MaxSection.isTabEnabled()` = раздел собран
  под эту архитектуру и не выключен переключателем в настройках GramBas (`grambas_max_tab`,
  по умолчанию включён, применяется после перезапуска). Иконка — статическая
  `drawable/grambas_tab_max.xml`, enum `GlassTabView.TabAnimation.MAX`;
- во вкладке `MaxDialogsFragment(inTab = true)`: шапку раскладывает сам
  (`actionBar.setAddToContainer(false)`, ViewPager её не сдвигает), снизу отступ
  `DialogsActivity.MAIN_TABS_HEIGHT_WITH_MARGINS` + панель навигации. Без входа — экран
  «Войти в MAX», вход открывается с `MaxLoginFragment(fromTab = true)` и просто
  закрывается обратно;
- счётчик непрочитанных на вкладке и на иконке приложения: модуль MAX зовёт
  `MaxSection.notifyUnreadChanged()` (из `MaxClient.chatsChanged`), слушатели — вкладка и
  `NotificationsController.updateBadge`; `setBadge` прибавляет `MaxSection.getUnreadCount()`;
- уведомление MAX — явный интент на `org.telegram.ui.LaunchActivity` с действием
  `org.telegram.max.OPEN_CHAT` и extra `MaxSection.EXTRA_CHAT_ID`; `handleIntent` после
  сборки главного экрана открывает `MaxSection.createChatFragment(chatId)`.

Грабли, все уже в коде:

- `cargo-ndk` читает манифест из текущего каталога, поэтому шаг CI заходит в каталог
  крейта и задаёт выход абсолютным путём;
- модулю нужен явный `androidx.core` на classpath, иначе Kotlin не видит супертипы
  вендоренного RecyclerView;
- «сессия не открыта» на устройстве: перед каждым запросом вызывается
  `connectIfNeeded()`, а экран входа поднимает соединение сразу в `createView`. До
  рукопожатия сервер не принимает ни запрос кода, ни вход;
- данные грузим из `createView`, а не из `onFragmentCreate`: там поля экрана ещё не
  созданы и ответ, пришедший раньше вёрстки, ронял фрагмент. Плюс проверки
  `isInitialized` в обработчиках пушей;
- `api2.oneme.ru` отдаёт сертификат Минцифры, которого нет в хранилище Android. Без
  `Kolibri.setTrustMincifryCa(true)` TLS падает с UnknownIssuer и рукопожатия не будет.
  Флаг общий на процесс, ставится в `MaxClient.configureCore()` до первого соединения,
  рядом задаётся `setDnsCachePath` (кеш адресов переживает перезапуск и спасает при
  подменённом DNS). Системное хранилище ядро не трогает;
- R8 вырезал `ru.kolibri.KolibriException`: из Kotlin его никто не создаёт, бросает
  только Rust через `FindClass`. В релизе вместо текста ошибки приходил
  `NoClassDefFoundError` с именем класса, и настоящая причина была не видна. Лечится
  `TMessagesProj_Max/consumer-rules.pro` (`-keep class ru.kolibri.**`), он подключён
  через `consumerProguardFiles`. Любой новый класс, который существует только для
  нативной стороны, туда же;
- тексты ошибок на экранах идут через `MaxLog.describe`: у исключения может не быть
  сообщения, тогда показываем причину или имя класса, а не пустую строку;
- **эталон — Komet** (github.com/KometTeam/komet, работает у пользователя). Параметры
  клиента сверены с ним построчно, и при любых странностях со входом первым делом
  сравнивать с ним, а не гадать. Где что лежит у Komet: хост —
  `lib/core/config/config.dart`, версия — `lib/core/storage/spoofing_service.dart`,
  хеши отпечатка — `lib/core/protocol/chat_cache_fingerprint.dart`, идентификаторы —
  `lib/core/storage/device_identity.dart`, рукопожатие — `_buildSessionOptions` в
  `lib/backend/api.dart`, запросы входа — `lib/backend/modules/account.dart`;
- хост `api2.oneme.ru` (основной, как у Komet), `api.oneme.ru` запасной;
- версия и хеши отпечатка — **согласованная пара**: хеши dex и so меняются от версии к
  версии. Сейчас 26.23.2 (6779) с хешами от неё. Умолчание ядра 26.20.2 сервер
  отшивает «Приложение устарело». Если это повторится, брать новую пару из Komet
  целиком. Поднять только версию нельзя: так было в v2.4.4–v2.4.6 (26.38.2 при хешах
  от 26.20.2), и сервер принимал запрос кода, выдавал токен, а код не отправлял;
- `deviceId` — 16 hex-символов (формат Android ID), `instanceId` — отдельный UUID,
  `clientSessionId` — случайный на запуск, имя устройства «производитель модель».
  С UUID в deviceId и константным clientSessionId код тоже не приходил;
- `callsSeed` из рукопожатия обязателен: из него считается отпечаток. Рукопожатие без
  него — ошибка, запрос кода без отпечатка не отправляется;
- **соединение как у Komet**: `autoReconnect = false`, на каждое соединение новая
  `Session`, сразу после рукопожатия вход по токену (`ensureOnline` под `connectLock`),
  раз в 3 секунды проверка живости с переподключением по нарастающей задержке. С
  автопереподключением ядра сессия после обрыва поднималась без входа, и на любой
  запрос сервер отвечал «Недопустимое состояние сессии». Повторный вход в той же
  сессии сервер тоже не принимает, поэтому «Обновить» сбрасывает сессию и входит
  заново. Запрос, упавший из-за мёртвой сессии, повторяется один раз после
  переподключения (`isSessionProblem`).

Вверху экрана входа — строка подключения: внешний IP со страной и флагом
(`MaxIpCheck`, ipwho.is с запасным ipinfo.io, обычный HTTPS мимо ядра) и то, кем нас
видит сам MAX: `location` и `isVpn` из ответа рукопожатия. Нажатие перепроверяет IP.

На экране входа под кнопкой показывается ответ сервера как есть (`MaxClient.diagnostics`,
копируется долгим нажатием). Это временная диагностика на время обкатки раздела: лог
приложения с телефона не достать, а тихие отказы сервера видны только в его ответе.

Регистрация в разделе есть, и это важно для текстов: вход и регистрация в MAX — один
и тот же путь (номер -> код), развилка только после кода. Экран входа не должен писать
«номер, на который зарегистрирован MAX», иначе пользователь думает, что регистрации
нет.

Регистрация нового номера есть: после кода сервер возвращает токен типа REGISTER,
дальше шаг с именем и фамилией и опкод 23 (`authConfirm`).

Облачный пароль (двухфакторный вход) есть, сверен с Komet: после кода сервер вместо
токена присылает `passwordChallenge` с `trackId` и подсказкой `hint`. Пароль уходит
опкодом 115 (`authLoginCheckPassword`) с `trackId` и `password`, в ответ — обычный
`tokenAttrs.LOGIN.token`. Поле `error` в ответе — неверный пароль. Порядок проверки
ответа на код как у Komet: пароль, потом регистрация, потом вход. Пароль не обрезается
по краям. Ответ на проверку кода в панель диагностики выводится только именами полей:
там бывает постоянный токен.

## Тон пользовательских текстов

Любой текст, который читает конечный пользователь — тело GitHub Release, окно
обновления в приложении, changelog — пишется простым языком без технического
жаргона. Никаких TLS, ECH, фрагментации, shaping. Описываем выгоду, а не
реализацию: «улучшенная маскировка трафика», «соединение труднее распознать и
заблокировать». Это прямое требование пользователя, применять по умолчанию.

## Механизм авто-апдейта и релиза

`.github/workflows/auto-update.yml`, раз в неделю или вручную. Сравнивает
`APP_VERSION_NAME` в корневом `gradle.properties` с upstream. При различии:
`git reset --hard upstream/master`, восстановление `.github/workflows`,
`patches/` и `CLAUDE.md` из предыдущего форк-коммита, наложение патча через
`git apply --3way`, коммит, тег, **force-push в master**, запуск `build.yml`,
уведомление в Telegram.

Force-push здесь сделан намеренно, это не поломка. Реальная история master —
много мелких инкрементальных коммитов на старом снапшоте upstream, а
авто-апдейт пересобирает состояние из свежего upstream плюс один большой патч.
Обычный merge через PR между этими двумя линиями невозможен, GitHub показывает
`mergeable_state: dirty` с тысячами конфликтов в сгенерированных upstream файлах
вроде TL-схем, а не в коде форка. На практике проверено: переналоженный патч
получился байт-в-байт тем же, что уже был в истории master, то есть код и фичи
не теряются, сворачивается только промежуточный лог коммитов. Старые ветки с
фичами и фиксами остаются на remote. Для будущих синхронизаций с upstream
использовать тот же подход, если пользователь не скажет иначе.

`build.yml` срабатывает на push тега `v*` либо вручную через
`workflow_dispatch` с обязательным `version_tag`; собирает release APK и
публикует GitHub Release. Ручной запуск нужен, когда тега ещё нет: тег создаёт
сам шаг публикации (`gh release create --target <sha>`). Тег с третьим
компонентом публикуется как prerelease. Если релиз для тега уже существует, APK просто перезаливается, а
вручную выставленные заметки не затираются. Дефолтный текст заметок захардкожен в
самом workflow, держать его простым по правилу выше. В checkout обязателен
`submodules: recursive`. Версия NDK в workflow должна совпадать с `ndkVersion`
в `TMessagesProj/build.gradle`: с 13.0.2 это 27.2.12479018. Апстрим больше не
собирает boringssl, ffmpeg и webrtc из исходников, а линкует готовые
статические библиотеки из `TMessagesProj/jni/prebuild/lib`; Rust-часть
`jni/gram-wallet` в сборку APK не входит.

Новый тег считается из последнего существующего: первое число — major, последнее —
minor, minor увеличивается на единицу. Сортировка `--sort=-v:refname`, так что
после ручного трёхкомпонентного тега вида `v2.2.1` очередной тег нужно поставить
руками.

## Состояние на 2026-10-20

Upstream 13.0.2, сборка 7175. Патч перенесён на эту базу, `master` обновлён,
релиз **v2.4** выпущен: обычный релиз (не prerelease), latest, APK 70 МБ,
собран из коммита 34148940. Клиенты на v2.3 и v2.2.1 получат его через
встроенный апдейтер. Тестовая сборка `v2.3.1` осталась prerelease.

Сборка на этой базе занимает от 50 минут до часа, разброс из-за раннера.

Web proxy в апстриме появился: пакет `org.telegram.utils.proxy`
(`ProxySettings`, `WebProxyTransport`, `WebProxyConnectionTester`), подключён
в `ProxySettingsActivity` и `ConnectionsManager`. Тип прокси в UI теперь
перечисление `ProxySettings.Type` вместо целых констант. Настройки маскировки
форка показываются только для MTPROTO.

Своя реализация веб-прокси, жившая в master на 12.10.1
(`org.telegram.messenger.WebProxyTransport`, MTProto поверх HTTPS с локальным
слушателем и токеном), на 13.0.2 сознательно НЕ переносилась: апстримная
закрывает ту же задачу, интегрирована в настройки прокси и не требует
поддержки на каждом обновлении. Два механизма с одним типом WEB не
сосуществуют без развязки типов и настроек. Код сохранён в ветке
`fork-web-proxy-12.10.1` (коммит f2aba199) — других веток с ним нет, так что
ветку не удалять.

Про автообновление у клиентов: `parseVersionCode` в `GithubUpdaterController`
считает `major * 1000 + minor` и третий компонент тега игнорирует, поэтому
`v2.3.1` для апдейтера равен `v2.3`. Плюс апдейтер читает
`/releases/latest`, а GitHub не отдаёт туда prerelease. Тестовые сборки
публиковать как prerelease.
